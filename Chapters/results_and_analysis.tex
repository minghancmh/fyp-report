\chapter{Chapter 5: Results and Analysis}

In this chapter, we will do a comparison between deploying a Kubernetes workload via the traditional approach and via \texttt{cloudkube}. While \texttt{cloudkube} was initially developed
to meet the needs of the ASR application, this FYP has met the stretch goal of making \texttt{cloudkube} extensible to different types of Kubernetes workloads. Consequently, the subsequent sections
will show the testing and deployment of the ASR application as well as a multi-service, fullstack application to infrastructure provisioned by \texttt{cloudkube}. 

\section{Deployment Timeline}
This subsection will compare the deployment timeline using \texttt{cloudkube} vs the traditioanal manual approach, highlighting the time savings and operational benefits. 
The estimated times presented here are based on my experience, as well as anecdotal, unstructured evidence with other students working on deployment of SpeechLab applications.
As such, they serve as a general guide rather than absolute values, as actual deployment durations vary depending on specific infrastructure configurations, as well as expertise
in cloud technologies. In this section, we see that \textbf{deploying with \texttt{cloudkube} provides a much gentler learning curve and much quicker deployment times. }

\subsection{Traditional Method}

In the context of this subsection, the traditional method of deploying a Kubernetes workload to the cloud refers to using the AWS CLI or AWS Console for manual setup and management.
Due to time and resource constraints, this FYP is focused solely on AWS Cloud, and all deployment/learning times peresented here are based on my personal experience with AWS, and may vary
depending on individual familiarity with the platform and cloud specific technologies.

\subsection{\texttt{cloudkube} Method}

As we can see from Table \ref{table:k8s-cluster-cloudkube}, the learning curve with \texttt{cloudkube} is made more gentle, and execution times are drastically reduced as compared to the 
traditional method (Table \ref{table:k8s-cluster-setup}). Furthermore, the bulk of the time taken as presented in Table \ref{table:k8s-cluster-cloudkube} is for the installation of prerequisites.
Once a developer has set up his/her local environment with \texttt{cloudkube} and its corresponding dependencies, it takes \textbf{no more than 20 minutes} to get a fully
functional Kubernetes cluster in the cloud.  The full workflow with \texttt{cloudkube} can be found in Appendix \ref{appendix:cloudkube-readme}.

\section{Deployment of SpeechLab ASR Application}

This section will cover the deployment of the SpeechLab ASR Application via \texttt{cloudkube}. In this evaluation, we will walkthrough the end-to-end deployment process, as well as testing
the API exposed by the SpeechLab ASR Application to ensure that the infrastructure provisioned suitably fits the needs of the application.

First, \texttt{cloudkube} is downloaded via \texttt{pip install cloudkube}. We then configure our cloud credentials using \texttt{aws configure}. Pictures for this step
are omitted form this report to keep the aws credentials secret. 
Next, based on the Kubernetes manifest of the SpeechLab ASR Application (Appendix \ref{appendix:asr-archi}), we see that persistent volumes are required. 
The ASR application also runs on \texttt{x86} architecture as dictated by the decoding-sdk.
\texttt{cloudkube init} is then run, and \texttt{cloudkube} is configured (via option \texttt{2}) with \texttt{x86} machines, and PersistentVolume setup (Figure \ref{fig:cloudkube-init-2}). 
At this point, configuring the cluster has taken no more than 5 minutes. Next, option \texttt{3} is run, and \texttt{cloudkube} begins provisioning our Kubernetes cluster in the cloud. 

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.8\textwidth]{fig/cloudkube-init-2.png}
    \caption{Configuring Kubernetes cluster for SpeechLab ASR Application via \texttt{cloudkube}}
    \label{fig:cloudkube-init-2}
\end{figure}

The cluster creation process takes approximately 10 minutes. Once the Kubernetes cluster is successfully created (Figure \ref{fig:cloudkube-success}), we can then navigate to the Kubernetes manifests
to run \texttt{kubectl apply -f manifest.yaml}. At this point, our application is deployed to the cloud, and ready for testing. It should be noted that the 
images are stored on Dockerhub, while the models are pulled from an S3 bucket in our AWS cloud. 

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.8\textwidth]{fig/cloudkube-success.png}
    \caption{\texttt{cloudkube} Successful Provisioning}
    \label{fig:cloudkube-success}
\end{figure}

\begin{figure}[h!]

As we can see from the output of \texttt{kubectl get pods -A} (Figure \ref{fig:asr-apply}), which queries the cluster for all pods in all namespaces, we see that all the pods have status of 
\texttt{RUNNING}, meaning that they have successfully started. Of note are the pods in the \texttt{decoding-sdk} namespace, which show the successful starting of the
master pod (\texttt{decoding-sdk-server-6889cd66c5-84d54}) as well as the 2 worker pods (\texttt{decoding-sdk-worker-5bdd4bd4db-hv8wp} and \texttt{decoding-sdk-worker-5bdd4bd4db-k7fmh}).
The \texttt{kube-system} namespace also contains pods relevant for mounting of the PersistentVolume. These are the \texttt{efs-csi-controller} and \texttt{efs-csi-node} pods. 

\begin{figure}[h!]
    \centering

Figure \ref{fig:asr-describe-pod} shows event log for one of the worker pods. In this event log, we see that a container \texttt{copy-models} is started.
This container pulls the images from the existing S3 bucket that we have in the AWS cloud into the machine. The decoding-sdk server is then started.


All of the above outputs show that the decoding-sdk server has successfully started, and the SpeechLab ASR Application is successfully deployed. Lastly, we will
hit the endpoint of the application to confirm that the live transcription works. To do this, we first need to view the load balancer exposed to the public internet.
This can be done via \texttt{kubectl get services}. As we can see from the output of Figure \ref{fig:asr-svcs}, the external IP of the decoding-sdk server is 
\texttt{ad40289733a2844058b1f62d619b7c8e-1622439313.ap-southeast-1.elb.amazonaws.com}.

Finally, we can hit the endpoint and obtain our live transcription as shown in Figure \ref{fig:live-transcribe}. 

\begin{figure}[h!]

All in all, this deployment process took no longer than 20 minutes. Using \texttt{cloudkube}, developers are able to quickly spin up a Kubernetes cluster in the cloud and test their application in a scalable and isolated environment.

\section{Deployment of Multi Service Dummy Application}
Next, we will look at the deployment of a multi-service, dummy application that was created for the purposes of testing the various functionality within the 
Kubernetes cluster provisioned by \texttt{cloudkube}. The architecture diagram of this application is shown in Figure \ref{fig:tasks-app}. Traffic from the 
public internet is routed through an ingress, which directs traffic between the relevant pods for servicing. 
The roles and responsibilities of each Kubernetes component is shown in Table \ref{table:tasks-app}.

\begin{figure}[h!]
    \centering
    \includegraphics[width=0.8\textwidth]{fig/tasks-app.png}
    \caption{Multi Service Tasks Application Architecture Diagram}
    \label{fig:tasks-app}
\end{figure}

\begin{table}[h]
    \centering
    \renewcommand{\arraystretch}{1.3} % Adjust row height for better readability
    \begin{tabular}{|p{3cm}|p{5cm}|p{6cm}|}
        \hline
        \textbf{Name} & \textbf{Kubernetes Component} & \textbf{Responsibility} \\
        \hline
        \texttt{-} & \texttt{Ingress} & Routing rules for routing traffic to the various pods \\ 
        \hline
        \texttt{tasks service} & \texttt{Pod} & Creation and Deletion of Tasks \\
        \hline
        \texttt{users service} & \texttt{Pod} & Registering and Logging in Users \\
        \hline
        \texttt{frontend pod} & \texttt{Pod} & UI layer for interaction with the application \\
        \hline
        \texttt{auth service} & \texttt{Pod} & Dummy authentication service to verify tokens during login \\
        \hline
        \texttt{tasks storage} & \texttt{PersistentVolumeClaim} & Claims a set amount of storage from the PersistentVolume \texttt{Database} for storing of tasks\\
        \hline
        \texttt{users storage} & \texttt{PersistentVolumeClaim} & Claims a set amount of storage from the PersistentVolume \texttt{Database} for storing of users \\
        \hline
        \texttt{Database} & \texttt{PersistentVolume} & Provides persistence of data across pod restarts \\
        \hline
    \end{tabular}
    \caption{Responsibilities of each component in tasks application}
    \label{table:tasks-app}
\end{table}

To successfully deploy this application, we need to provision an ingress controller to satisfy the ingress Kubernetes resource. Furthermore, this application 
also runs on \texttt{arm}, and the architecture of the cluster must be changed. To do this, we simply edit the \texttt{config.json} file to the following. As we can see,
an nginx ingress controller has been chosen, and the architecture has changed to \texttt{arm}.

\newpage
\begin{lstlisting}[caption={\texttt{config.json} file for Tasks dummy application}]
{
    "region": "ap-southeast-1",
    "prefix": "mh-dep-test",
    "architecture": "AL2_ARM_64",
    "ingressController": "aws-nginx-ingress-controller",
    "requireEFS": "True"
}       
\end{lstlisting}

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{fig/tf-tasks.png}
    \caption{Terraform output for provisioning with \texttt{cloudkube}}
    \label{fig:tf-tasks}
\end{figure}

Next, we run option 3 of \texttt{cloudkube init} to provision the resources.
As seen in Figure \ref{fig:tf-tasks}, the cluster is modified accordingly. Note that only resources that need modification are changed. Other resources are left
alone to avoid redundant re-creation. Once again, the infrastructure provisioning happens in less than 10 minutes, and the Kubernetes manifest of this application
can now be applied to the cluster.

Once the Kubernetes manifest is applied to the cluster, we can then access the frontend of our application via the ingress provisioned. The address of this ingress can be 
output by doing \texttt{kubectl get ingress}. We can test the functionality of the application through this frontend interface, as well as through postman.

\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{fig/task-creation.png}
    \caption{Successful creation of tasks}
    \label{fig:tasks-creation}
\end{figure}

From Figure \ref{fig:tasks-creation}, we can see that we are able to create new tasks. Inspecting the nginx ingress controller logs also shows a rerouting to the various 
services based on the Kubernetes Ingress component. Finally, in order to test that the PersistentVolume setup is working, the pods are intentionally killed. With
PersistentVolumes, the tasks persist across pod lifecycles, confirming functionality of the PersistentVolumes which are realised by EFS under the hood of \texttt{cloudkube}.
